You are using Claude Code to accelerate software development. Your team uses it for code generation, refactoring, debugging, and documentation. You need to integrate it into your development workflow with custom slash commands, CLAUDE.md configurations, and understand when to use plan mode vs direct execution.

A security audit requires updating your authentication library from v2 to v3. The migration guide documents breaking changes: authenticate() now returns a Promise instead of accepting a callback, the User type has restructured fields, and three deprecated methods were removed. Grep shows the library is imported in 45 files across several modules.

What's the most effective approach?

A.
Enter plan mode to explore library usage across modules, map affected code paths, then create a migration strategy before implementing.
B.
Create a custom slash command encapsulating the migration transformations, then execute it against each file without prior codebase exploration.
C.
Update the dependency version, run the test suite, and use Claude Code to fix each failure as it appears.
D.
Paste the migration guide's breaking changes into your prompt and use direct execution to update all usages across the 45 files.
A
Explanation

The key phrases are: Breaking changes across signatures & types (authenticate() callback → Promise, User fields restructured, deprecated methods removed) 45 files across several modules * When to use plan mode vs direct execution

In Claude Code, Plan Mode is specifically designed for multi-file architectural changes and complex refactorings where upfront investigation prevents cascading errors.

A good Claude Code workflow for this migration is: 1. Enter Plan Mode (read-only exploration) 2. Trace all 45 imports of the authentication library 3. Map caller signatures affected by the callback-to-Promise conversion 4. Identify downstream consumers of the restructured User fields 5. Group changes by module and dependency order 6. Review and approve the migration strategy before executing edits

Because changing a function from callbacks to Promises alters async control flow up the call stack, mapping affected code paths first ensures a cohesive, phased implementation rather than piecemeal fixes.

B
Explanation

Custom slash commands are designed for repeatable, standardized workflows (such as generating a new component or running a standard PR checklist)—not one-off major library upgrades. Furthermore, executing transformations file-by-file without prior codebase exploration ignores how caller functions and downstream modules depend on the changed User type and async signatures.

C
Explanation

Relying purely on test failures ("fix-as-you-go") is reactive and risky for structural changes: Test suites rarely cover 100% of code paths. Unhandled Promise rejections or subtle type mismatches in untested modules will slip through. * Fixing errors one by one often results in inconsistent patterns across the 45 files.

D
Explanation

This is the tempting shortcut, but direct execution across 45 files without prior exploration frequently leads to: Context-window exhaustion mid-refactor Inconsistent async/await patterns across modules * Half-completed migrations that are hard to roll back when edge cases appear

💡 Key Learning Point

For Claude Code workflow questions:

Scenario | Usually Correct | Multi-file refactoring / breaking API changes | Plan Mode first, then execute | Large-scale architectural migrations | Explore & map code paths before editing | Small, isolated, well-scoped bug fix or feature | Direct execution | Repeatable team workflows / boilerplate | Custom slash commands

Since this involves breaking changes across 45 files and multiple modules, Anthropic favors: ✅ A. Enter plan mode to explore library usage across modules, map affected code paths, then create a migration strategy before implementing.

What's the most effective approach to improve the agent's selection of MCP tools?

A.
Expand MCP tool descriptions to detail capabilities and outputs—e.g., "Builds dependency graph showing direct imports, transitive dependencies, and cycles."
B.
Split analyze_dependencies into granular tools (list_imports, resolve_transitive_deps, detect_circular_deps) so each has a focused purpose less likely to overlap with Grep.
C.
Add routing instructions to the system prompt specifying that dependency-related questions should use MCP tools rather than Grep.
D.
Remove Grep from available tools when the MCP server is connected to eliminate functional overlap.
A
Explanation

The key phrases are: Server is healthy and tools appear in tools/list Agent consistently uses Grep instead of analyze_dependencies MCP analyze_dependencies - "Analyzes dependency graph" (vague, 3-word description) Built-in Grep - detailed description

LLM tool selection is driven primarily by the tool schemas and descriptions provided in the tool definitions. When a built-in tool has a clear, concrete description and an MCP tool has an underspecified one, the model defaults to the tool whose behavior and output it understands best.

Expanding the MCP tool description clarifies: 1. What it does: Builds a full dependency graph (not just text matching) 2. What it returns: Direct imports, transitive dependencies, and circular dependency cycles 3. When it beats Grep: Anytime structural relationships—rather than raw line matches—are needed

B
Explanation

Splitting one cohesive tool into three granular tools (list_imports, resolve_transitive_deps, detect_circular_deps) increases tool-selection overhead and forces the agent to orchestrate multiple calls. Worse, list_imports still overlaps conceptually with Grep if its description remains vague.

C
Explanation

Adding hardcoded routing rules to the system prompt is a brittle workaround for poorly documented tools: System prompt instructions compete with other context and can degrade as conversations grow. Rigid rules ("always use MCP instead of Grep") prevent the agent from combining both tools when a query genuinely needs regex search alongside dependency analysis.

D
Explanation

Removing Grep cripples the agent for general codebase exploration. Grep is essential for finding string literals, error messages, configuration keys, and non-import patterns across legacy systems.

💡 Key Learning Point

For MCP & Tool Selection questions:

Scenario | Usually Correct | Agent ignores a healthy MCP tool in favor of a built-in tool | Improve/expand the MCP tool description | Tool outputs or edge cases are misunderstood by the model | Add explicit capabilities, inputs, and return formats to the tool schema | Hardcoding tool preference rules in the system prompt | Usually an anti-pattern (brittle) | Disabling built-in tools to force MCP usage | Usually an anti-pattern (reduces capability)

Since the MCP tool description was too brief compared to Grep, Anthropic favors: ✅ A. Expand MCP tool descriptions to detail capabilities and outputs.

It must handle edge cases gracefully and integrate with downstream systems.

Your extraction pipeline processes restaurant menus and must output structured JSON with fields for item names, descriptions, prices, and dietary tags. Some menus use inconsistent formatting—prices as "$12" vs "12.00", dietary info as icons vs text.

What's the most reliable approach?

A.
Define a strict output schema and include format normalization rules in your prompt.
B.
Extract data as-is and normalize formats in post-processing code after Claude returns.
C.
Request multiple extraction attempts per document and select the most common format.
D.
Use separate extraction calls for each field to ensure consistent handling of each type.
A
Explanation

The key phrases are: Validates the output using JSON schemas Inconsistent formatting—prices as "$12" vs "12.00", dietary info as icons vs text * Integrate with downstream systems

Reliable structured extraction requires combining structural guarantees with semantic normalization: 1. Strict output schema: Enforces exact property names, data types (e.g., number for price, array of enum strings for dietary tags), and required fields so downstream systems never break on malformed JSON. 2. Format normalization rules in the prompt: Instructs Claude how to standardize messy inputs during extraction (e.g., "Strip currency symbols and output prices as decimals like 12.00; map leaf icons or (V) to 'vegetarian'").

Because Claude sees the full visual/textual context of the menu item, it can resolve ambiguous icons and currency formats accurately at generation time.

B
Explanation

Extracting data "as-is" and normalizing in post-processing code fails when semantic or visual context is lost: A regex or parser cannot reliably interpret arbitrary menu icons or layout-dependent dietary notes once flattened into raw strings. Unconstrained extraction risks failing JSON schema validation before post-processing even runs.

C
Explanation

Running multiple extraction attempts per document and picking the "most common format": Multiplies latency and API token costs. Does not fix systematic ambiguity—if an icon is unclear without normalization rules, majority voting simply picks the most frequent guess rather than a standardized target format.

D
Explanation

Making separate extraction calls for each field (item_name, description, price, dietary_tags): Increases latency and cost by 4x. Breaks row/item alignment across multi-column menus because each call extracts fields in isolation without shared item context.

💡 Key Learning Point

For Structured Data Extraction questions:

Scenario | Usually Correct | Messy/inconsistent source formats + downstream integration | Strict JSON schema + prompt normalization rules | Guaranteeing valid JSON structure and field types | Strict output schema / Structured Outputs | Interpreting ambiguous symbols, icons, or domain variants | Explicit normalization rules in prompt | Multiple calls per field or majority-voting retries | Usually anti-patterns (high cost/latency, breaks context)

Since the pipeline needs both schema compliance and consistent normalization of messy menu formats, Anthropic favors: ✅ A. Define a strict output schema and include format normalization rules in your prompt.

Your system has been operating with 100% human review for 3 months. Analysis shows that extractions with model confidence ≥90% have 97% accuracy overall. To reduce reviewer workload, you plan to automate high-confidence extractions.

Before deploying, what validation step is most critical?

A.
Compare accuracy at different confidence thresholds (85%, 90%, 95%) to find the optimal cutoff that maximizes automation while minimizing errors.

Verify that 97% accuracy meets requirements for all downstream systems that consume the extracted data.
C.
Analyze accuracy by document type and field to verify high-confidence extractions perform consistently across all segments, not just in aggregate.
D.
Run a two-week pilot routing 25% of high-confidence extractions directly to downstream systems and monitor error reports.
A
Explanation

Tuning global confidence thresholds (85%, 90%, 95%) still relies on a single aggregate cutoff. If a specific document type or critical field is overconfident (e.g., 96% confidence but only 75% accurate), raising the global threshold won't selectively protect that weak segment without unnecessarily blocking easy documents.

B
Explanation

Checking whether 97% meets downstream SLAs assumes that the 97% rate holds uniformly across all data slices. Downstream systems typically have different error tolerances per field (e.g., a corrupted account_number is fatal, whereas a minor description typo is harmless), so an aggregate 97% figure is insufficient without field- and segment-level breakdown.

C
Explanation

The key phrases are: 100% human review for 3 months (you already have rich historical ground-truth labels) 97% accuracy overall (aggregate metric) * Before deploying, what validation step is most critical?

Aggregate accuracy (97% overall) frequently hides Simpson's Paradox / slice-level blind spots in production extraction pipelines: 1. Document-Type Skew: Common, simple document templates (e.g., standard invoices) might achieve 99.5% accuracy and dominate the volume, masking the fact that complex or rare document types (e.g., handwritten receipts or multi-page contracts) only achieve 70% accuracy even when the model reports ≥90% confidence. 2. Field-Level Disparities: Non-critical fields (vendor_city) might be 99% accurate while high-impact fields (total_amount, tax_id, due_date) have a much higher error rate among high-confidence predictions. 3. Zero-Risk Offline Validation: Because you already have 3 months of human-reviewed data, slicing historical accuracy by document_type and field catches miscalibrated confidence segments before any unreviewed data touches downstream systems.

D
Explanation

Routing 25% of unreviewed extractions straight to downstream systems is a live production rollout, not a pre-deployment validation step—and it exposes downstream systems to silent data corruption if errors aren't immediately caught or reported. Moreover, you already have 3 months of human-reviewed ground-truth data to analyze offline safely.

💡 Key Learning Point

For Claude Evaluation, Confidence Calibration & Production Rollout questions:

Scenario | Usually Correct | High aggregate accuracy reported before automating human-in-the-loop | Disaggregate / slice accuracy by document type and field | Historical human-reviewed data already exists | Perform segmented offline evaluation before live routing | Relying solely on global thresholds or overall averages | Usually a trap (masks overconfident edge-case slices) | Live A/B or canary rollout before validating segment performance | Premature (exposes downstream systems to unvalidated errors)

Since aggregate accuracy (97% overall) can mask poorly calibrated confidence on specific document types or critical fields, Anthropic favors: ✅ C. Analyze accuracy by document type and field to verify high-confidence extractions perform consistently across all segments, not just in aggregate.

An engineer asks the agent to find all callers of a function before removing it. The function is defined in a core library but is also exposed through wrapper modules that rename the function for domain-specific use (e.g., calculateTax in the library becomes computeOrderTax in the orders module).

What exploration strategy will most reliably identify all callers?

A.
Use Grep to find all files that import from the library or wrapper modules, then read each file to check whether it uses the function.
B.
Read the library and wrapper modules to identify all exposed names for the function, then Grep for each name across the codebase.
C.
Use Grep to search for the function's original name across the codebase.
D.
Search for the function name in project documentation to understand intended usage patterns and navigate to documented integration points.
A
Explanation

A is far less efficient and harder to scale: Finding every file that imports anything from the core library or wrapper modules can match hundreds of files in a large codebase (most of which import unrelated utilities). Reading every single importing file just to check whether one function is used wastes context tokens and risks missing indirect re-exports.

B
Explanation

The key phrases are: Find all callers of a function before removing it Defined in a core library * Exposed through wrapper modules that rename the function (calculateTax → computeOrderTax)

If you search only for calculateTax, you will miss renamed usages like computeOrderTax(order). A reliable dependency-tracing workflow first maps all exported aliases before searching:

Explanation

Lowering the sentiment threshold (escalate for profanity, not general anger) tweaks a fundamentally flawed approach:

  • A very polite customer with a complex unauthorized request still needs escalation
  • A very angry customer requesting a simple password reset still doesn't
  • Threshold tuning is a local optimization on a globally wrong signal

Explanation

The root cause is using sentiment as an escalation criterion when sentiment has no bearing on whether the agent can resolve the issue. The fix is to replace sentiment-based escalation with objective, task-based criteria:

Escalation Trigger | Appropriate? | Reason | Policy gap (request requires approval beyond agent scope) | ✅ Yes | Task genuinely cannot be completed by the agent | Capability limit (agent lacks tools/data to complete task) | ✅ Yes | Task genuinely cannot be completed by the agent | Explicit human request ("I want to speak to a person") | ✅ Yes | Customer's direct preference must be honored | Customer uses angry language | ❌ No | Sentiment is independent of task complexity

  • Is an unauthorized financial action (the customer requested a password reset, not a refund)

  • Addresses tone, not the actual escalation logic problem

  • Does not address when escalation should trigger

In an extended codebase exploration session, Claude begins returning inconsistent answers and forgetting specific classes discovered earlier.

Which combination of features best addresses this context degradation?

A.
Utilizing /clear and increasing the temperature parameter to 1.0.
B.
Relying entirely on the Message Batches API for asynchronous context processing.
C.
Using scratchpad files to persist key findings and using the /compact command to reduce context usage.
D.
Spawning parallel subagents without providing them explicit context.
A
Explanation

/clear + increasing temperature to 1.0:

  • /clear wipes the entire context window — destroys all discovered classes, traced relationships, and exploration history
  • Temperature 1.0 increases output randomness — the opposite of what's needed when the problem is inconsistent answers
  • Higher temperature amplifies inconsistency; it doesn't cure it
  • Both actions make context degradation worse, not better
B
Explanation

The Message Batches API:

  • Designed for processing large numbers of independent requests in parallel asynchronously (e.g., classifying 10,000 documents overnight)
  • Has no mechanism for managing context state within an ongoing interactive session
  • Does not address context window saturation or recall degradation during exploration
C
Explanation

Context degradation in a long exploration session has two distinct causes — and option C addresses both:

Problem 1: Key findings get diluted as raw file content accumulates → Scratchpad files solve this by externalizing key discoveries: - Write discovered class names, relationships, and patterns to files as the session progresses - External files persist regardless of context window pressure - When the main session degrades, the scratchpad is a durable, queryable record of what was found - This is the external memory pattern from Q11 and Q34

Problem 2: Context window fills with accumulated tool outputs and conversation turns → /compact solves this by compressing history: - Reduces context usage by compacting older turns while preserving essential information - Unlike /clear (which destroys everything), /compact retains key context in compressed form - Frees up context window space for continued exploration without losing prior findings

Together, they address both causes: ``text Scratchpad files = external persistent memory (survives context resets) /compact = reduced context window usage (preserves essential history) ``

D
Explanation

Spawning parallel subagents without providing explicit context:

  • Each subagent starts with zero knowledge of previously discovered classes and patterns
  • They would re-explore the same files from scratch, duplicating work
  • Q11 and Q34 established this explicitly: subagents need key findings in their initial context to contribute meaningfully
  • Blind subagent spawning is the anti-pattern — context-seeded spawning is the correct pattern
💡 Key Learning Point

Context Degradation Response | Appropriate? | Scratchpad files + /compact | ✅ Preserves findings externally + compresses window | /clear (complete wipe) | ❌ Destroys all prior exploration work | Increasing temperature | ❌ Amplifies inconsistency, doesn't reduce it | Message Batches API | ❌ For batch processing, not session context management | Subagents without context handoff | ❌ Each re-explores from scratch (Q11/Q34 anti-pattern)

For extended codebase exploration sessions facing context degradation:

```text Two-part strategy:

  1. External memory (scratchpad files): Discovered class names, relationships, patterns → written to file Survives context resets, queryable anytime +
  2. Context compression (/compact): Compresses accumulated conversation history Frees context window without losing essential state = Session can continue deeper without degradation ```

Therefore, the best answer is:

✅ C. Using scratchpad files to persist key findings and using the /compact command to reduce context usage.

A developer wants to create a reusable behavior for performing extensive, multi-step codebase refactoring. The behavior needs to explore the codebase without polluting the main conversation's context window.

Which extension mechanism should be used?

A project-scoped CLAUDE.md configuration file.

A skill defined in a SKILL.md file with context: fork in its frontmatter.

A PostToolUse hook running a background Bash script.

Explanation

Custom commands in .claude/commands/:

  • Run within the main conversation context — all file reads and tool outputs accumulate in the same context window
  • No built-in mechanism to isolate the command's execution from the main conversation
  • Useful for simple, targeted commands that don't generate significant context pollution
  • Doesn't satisfy "without polluting the main conversation's context window"

Explanation

CLAUDE.md is a configuration/context file, not an execution mechanism:

  • Provides always-loaded guidelines, conventions, and project context

  • It's a passive document, not an active behavior

Explanation

The two requirements map to two distinct properties:

Requirement | Mechanism | Reusable behavior — invocable by any team member, any time | Defined in SKILL.md (project-committed, slash-command invocable) | Without polluting the main context window | context: fork in frontmatter — runs in isolated forked context

---
name: refactor-module
description: Performs extensive multi-step codebase refactoring
context: fork
---

The skill runs in a forked context window that: - Inherits the current session state (knows the codebase, the current task) - Isolates all tool outputs, file reads, and exploration traces from the main conversation - Completes without filling the main window with hundreds of intermediate file reads - Returns only the final result to the main conversation

  • Hooks are designed for deterministic side effects (run Prettier after TypeScript edits, block tool calls that exceed thresholds) — not complex exploration workflows
  • Running Bash in the background doesn't address the main conversation context pollution issue

Mechanism | Reusable? | Isolates Context? | Use For | SKILL.md with context: fork | ✅ Yes | ✅ Yes | Extensive multi-step operations requiring context isolation | .claude/commands/ custom command | ✅ Yes | ❌ No (runs in main context) | Simple, targeted commands | CLAUDE.md | ❌ Not invocable | N/A | Always-loaded project guidelines | PostToolUse hook | ❌ Not user-invocable | N/A | Deterministic side effects on tool events

        ↓

        ↓

A pull request modifies 14 files across a repository. A single-pass automated review produces inconsistent results, catching deep bugs in some files while missing obvious ones in others.

How should the review architecture be redesigned to fix this?

A.
Switch to a higher-tier model with a larger context window to process all files simultaneously.
B.
Require developers to manually split the PR into smaller submissions of 3-4 files.
C.
Split the review into focused passes: analyze each file individually for local issues, followed by a separate integration pass for cross-file data flow.
D.
Run three independent reviews on the full PR and only flag issues that reach consensus.
A
Explanation

Switching to a larger context window model:

  • Still reviews all 14 files in a single pass — attention is still distributed across the entire PR
  • The inconsistency is an attention distribution problem, not a context size problem
  • A model with twice the context window that processes all 14 files simultaneously may still review some files superficially and others deeply
  • Adds cost without addressing the architectural root cause
B
Explanation

Requiring developers to manually split PRs:

  • Shifts the architectural burden onto developers — adds friction without automating the solution
  • Legitimate related changes (like a refactoring that touches 14 files coherently) may not be splittable without losing review context
  • Doesn't address the review quality problem — a 3-4 file PR might still produce inconsistent results with the same single-pass architecture
  • Not a scalable automated solution
C
Explanation

The root cause of inconsistent single-pass reviews is attention dilution — when all 14 files compete for context window attention simultaneously, some files receive deep scrutiny while others receive only cursory coverage.

Multi-pass architecture directly fixes this by giving each scope its own focused pass:

```text Pass 1: Per-file local review (run in parallel) File 1 → dedicated review pass → local bugs found File 2 → dedicated review pass → local bugs found ... File 14 → dedicated review pass → local bugs found (each file gets full attention, not 1/14th of it)

Pass 2: Integration review (cross-file data flow) Receives summaries from Pass 1 + focuses on cross-module interactions, shared state, API contracts ```

Pass 1 (per-file) eliminates the inconsistency — every file receives equal, undivided attention rather than competing with 13 others for the model's focus.

Pass 2 (integration) catches what per-file reviews miss — cross-file issues like incorrect function call contracts, shared mutable state, and data flow errors that span module boundaries.

Together, the two-pass architecture provides comprehensive coverage at both levels without the attention dilution of a single combined pass.

D
Explanation

Three independent full-PR reviews with consensus filtering:

  • Each of the three reviews still suffers from the same attention dilution problem — reviewing all 14 files in one pass
  • Consensus voting may actually reduce findings: a deep bug found by only 1 of 3 reviewers (due to attention variance) is filtered out as a minority finding
  • Addresses disagreement between reviews but not inconsistency within each review
  • Triples the cost without fixing the architectural root cause
💡 Key Learning Point

Approach | Addresses Attention Dilution? | Consistent Coverage? | Multi-pass (per-file + integration) | ✅ Yes — each scope gets dedicated attention | ✅ Yes | Larger context window (single pass) | ❌ No — still all 14 files competing | ❌ No | Manual PR splitting (developer burden) | ⚠️ Reduces scope but shifts work to humans | ⚠️ Depends on discipline | Consensus voting (3x full-PR reviews) | ❌ No — each review still attention-diluted | ❌ May filter valid findings
