Which code snippet correctly implements a 'PreToolUse' hook in a Claude Code project to block any shell command containing 'rm -rf'?
A.
A PostToolUse hook that undoes the rm -rf command after it has run.
B.
A settings.json hook with type 'command' that runs a shell script which reads the tool input from stdin, checks for 'rm -rf' in the command parameter, and exits with code 2 (writing a reason to stderr) to block execution.
C.
Adding 'rm -rf' to the list of banned keywords in the system prompt.
D.
A CLAUDE.md entry that says: 'Never run rm -rf commands.'
A
Explanation
Incorrect. A PostToolUse hook executes after the tool has already completed. For a destructive command like 'rm -rf', the files are deleted before the hook runs there is nothing to undo unless a separate backup exists. Prevention requires PreToolUse interception, not post-execution cleanup.
B
Explanation
Correct. This is the accurate, official implementation pattern. The settings.json hook configuration specifies a PreToolUse event with a Bash tool matcher and a command to execute. The shell script reads the tool input JSON from stdin (which contains the tool name and parameters), checks the command field for 'rm -rf', and exits with code 2 the specific exit code Claude Code uses to signal a blocking error. A descriptive message written to stderr is surfaced to Claude as the reason for the block.
C
Explanation
Incorrect. System prompt keyword banning is a probabilistic, model-level control. It instructs the model to avoid generating 'rm -rf' in its outputs, but the model can still construct equivalent commands (rm -r -f, find + delete, etc.) that achieve the same result. A hook-based approach inspects the actual command parameter at execution time and blocks any destructive pattern deterministically.
D
Explanation
Incorrect. CLAUDE.md provides text-based, advisory instructions to the model. It cannot intercept or block a Bash command at the system level. The model may follow this instruction most of the time, but it provides no deterministic guarantee especially in automated or adversarial contexts.
💡 Key Learning Point
The correct PreToolUse hook implementation for blocking dangerous Bash commands: (1) In .claude/settings.json, add a PreToolUse hook with matcher 'Bash' and a command pointing to your script; (2) The script reads stdin (JSON with tool_name and tool_input fields), parses the command parameter, and checks for the dangerous pattern; (3) On match, the script writes a reason to stderr and exits with code 2 the Claude Code blocking signal; (4) Claude Code surfaces the stderr message to the model and aborts the tool execution. Exit code 2 specifically signals 'blocked by hook' other non-zero codes signal errors. Reference: https://docs.anthropic.com/en/docs/claude-code/hooks Domain Claude Code Configuration & Workflows

Production data shows that in 12% of cases your agent skips get_customer entirely and calls lookup_order using only the customer's stated name, occasionally leading to misidentified accounts and incorrect refunds. What change would most effectively address this reliability issue?
A.
Add few-shot examples showing the agent always calling get_customer first, even when customers volunteer order details.
B.
Add a programmatic prerequisite that blocks lookup_order and process_refund calls until get_customer has returned a verified customer ID.
C.
Implement a routing classifier that analyses each request and enables only the subset of tools appropriate for that request type.
D.
Enhance the system prompt to state that customer verification via get_customer is mandatory before any order operations.
A
Explanation
Incorrect. Few-shot examples are a statistical nudge they raise the probability of correct behaviour but cannot guarantee 100% compliance. They will not prevent the remaining 12% (or new edge cases) from occurring because the underlying tool-call ordering is not enforced deterministically.
B
Explanation
Correct. Enforcing tool-call ordering at the application layer by making the API refuse to invoke lookup_order or process_refund unless a verified customer ID from get_customer is already present in session state is the only deterministic solution. It converts a probabilistic prompt rule into a hard system-level invariant.
C
Explanation
Incorrect. A routing classifier controls which tools are presented to the model but does not enforce the sequential execution order of those tools. Even after correct routing, the agent could still skip get_customer and call lookup_order directly because there is no programmatic gate blocking the out-of-order call.
D
Explanation
Incorrect. System prompt instructions are advisory. Because Claude is a probabilistic model, it can deviate from prompt-level rules in complex, multi-turn, or adversarial contexts. For a production financial workflow, probabilistic compliance is insufficient the system must be deterministically safe.
💡 Key Learning Point
When safety or accuracy in a production system depends on a specific tool execution order, the only reliable approach is to enforce that order programmatically, not through prompts. Programmatic prerequisites (e.g., checking that get_customer has succeeded before allowing lookup_order to be invoked) create deterministic guarantees that cannot be bypassed by model drift, prompt injection, or edge cases. Prompt-based rules and few-shot examples only increase the statistical likelihood of correct behaviour they cannot provide the guarantee required for financial transactions. When building a 'Researcher Agent', you want it to look at a website and then write a report. You use the 'Fetch' MCP server to get the website content. The agent is failing because the website returns 500KB of raw HTML with navigation menus, ads, and footers. What is the best solution?
A.
Use a different model with a larger context window.
B.
Implement server-side content extraction in the MCP tool to strip irrelevant HTML and return only the main article content.
C.
Increase the context window size of the model.
D.
Ask Claude to summarise the entire HTML to reduce its size.
A
Explanation
Incorrect. A larger context window is a workaround, not a solution. It allows more noise to be processed, not better content to be delivered. The fundamental issue that the raw HTML contains vastly more irrelevant content than useful content is not addressed by increasing the context window.
B
Explanation
Correct. The MCP server (or a custom wrapper around the Fetch tool) should extract only the meaningful content before returning it to the agent. Libraries like Readability (the algorithm behind Firefox Reader Mode), trafilatura, or newspaper3k can identify and extract the main article body, stripping navigation, ads, footers, and boilerplate. The agent receives clean prose instead of 500KB of HTML noise.
C
Explanation
Incorrect. A larger context window can accommodate more content, but it does not improve the signal quality of that content. Processing 500KB of HTML with navigation menus and advertisements provides poor signal-to-noise for a researcher agent the relevant article content is buried in irrelevant markup. More space for bad data is not a solution.
D
Explanation
Incorrect. Asking Claude to first summarise the raw HTML requires loading all 500KB into the context window before any processing occurs which defeats the purpose of reducing the data before it reaches the model. The noise is already in context when the summarisation happens, consuming tokens and degrading performance.
💡 Key Learning Point
Server-side content extraction in the MCP tool is the correct architectural approach for noisy web content. Implementation options: (1) Use Python's trafilatura library for article extraction; (2) Use the Readability algorithm (available in many languages); (3) Use newspaper3k for news articles. The extracted result clean article text, typically 5-50KB vs. 500KB raw HTML is returned as plain text or structured JSON. This reduces token costs, improves processing speed, and provides the agent with high-quality input for report generation. The rule: handle data transformation in the tool, not in the model. A customer support agent needs to search a knowledge base. You have two tools: 'search_faq' (fast, limited scope) and 'deep_search' (slow, comprehensive). The agent always uses 'deep_search', even for simple, common questions. What is the primary fix?
A.
Remove the 'deep_search' tool from the allowed tools list.
B.
Increase the temperature to give the agent more freedom in tool selection.
C.
Use 'strict: true' in the tool definition to ensure the input schemas are strictly validated.
D.
Update the tool descriptions to clearly articulate the scope and intended use case of each tool, including when 'search_faq' should be preferred.
A
Explanation
Incorrect. Removing deep_search eliminates a capability that the agent legitimately needs for complex queries. The goal is to teach the model to use the right tool for the right job which requires improving descriptions not to remove options that make the problem disappear.
B
Explanation
Incorrect. Increasing temperature makes the model's tool selection more random and unpredictable, not more principled. This might occasionally produce a correct selection by chance but would make the agent's overall behaviour less reliable and harder to reason about.
C
Explanation
Incorrect. The strict parameter in a tool definition controls whether the model's generated arguments must conform exactly to the input schema (preventing additional properties and ensuring required fields are present). It has no effect on which tool the model chooses to invoke that decision is driven entirely by the tool descriptions.
D
Explanation
Correct. The root cause of consistent wrong-tool selection is almost always ambiguous or overlapping tool descriptions. The fix is to make the selection criteria explicit in both descriptions. For example: search_faq 'Use this tool FIRST for any question that is likely to have a standard, pre-written answer. It searches a curated FAQ database and returns results in under 1 second.' deep_search 'Use this tool ONLY if search_faq returns no relevant results or the question is complex and specialised.'
💡 Key Learning Point
Tool descriptions are the single most important lever for controlling tool selection accuracy. When tool selection is wrong, the root cause is almost always the descriptions either they are too vague, they overlap in scope, or they fail to specify selection priority. The fix requires: (1) Explicit use-case boundaries in each description; (2) Priority guidance (e.g., 'Use this tool FIRST' or 'Use this tool ONLY IF'); (3) Specific examples of the types of queries each tool handles. This is more effective and maintainable than adding system-prompt examples or restricting tool availability. A developer is implementing a 'Code Review' agent using the Claude API. The agent is tasked with reviewing a pull request that contains 3 separate file changes. The developer wants the agent to review each file change independently to provide more focused feedback. Which approach is most appropriate?
A.
Use extended thinking to allow the agent to review all files in one comprehensive pass.
B.
Issue all three file review tasks as parallel tool calls in a single turn, allowing the agent to review all files simultaneously and provide unified feedback.
C.
Use the Message Batches API to submit all three file reviews as a batch job.
D.
Make three separate, sequential API calls one per file and manually combine the results.
A
Explanation
Incorrect. Extended thinking gives the model more internal reasoning tokens for a single generation. Reviewing all three files in a single comprehensive pass does not provide the independent, focused analysis the developer wants all three files share the same reasoning context, potentially causing one file's issues to influence the analysis of another. Separate, parallel reviews maintain independence.
B
Explanation
Correct. For three independent file reviews, parallel tool calls are the optimal approach. The agent issues all three review tool calls simultaneously in a single response turn. The application executes all three reviews concurrently, collecting independent, focused feedback for each file. The results are then synthesised into a unified review report. This is faster than sequential calls and provides independently focused analysis for each file.
C
Explanation
Incorrect. The Message Batches API is for asynchronous offline processing where results may be available hours later. Code reviews as part of a PR workflow require timely, interactive results. The Batches API introduces unnecessary latency and is not appropriate for developer workflow integrations requiring fast turnaround.
D
Explanation
Incorrect. Three separate sequential API calls means each file review waits for the previous one to complete the total review time is the sum of all three individual review times. This is the slowest approach and requires additional application logic to combine results. Parallel tool calls achieve the same independence with better performance.
💡 Key Learning Point
Parallel tool calls for independent subtasks provide the optimal balance of independence and performance. For a 3-file PR review: (1) The agent issues three review tool calls simultaneously; (2) The application executes all three reviews concurrently; (3) Each review is independent focused exclusively on its file with no cross-contamination from other files; (4) All three results are returned in a single response; (5) The agent synthesises the independent reviews into a unified PR assessment. Total time: the duration of the slowest single file review, not the sum of all three. A developer wants to use Claude Code to refactor a private repository that contains sensitive API keys. What is the recommended way to prevent Claude Code from accidentally exposing these keys?
A.
Store all API keys in a separate .env file and add a rule in CLAUDE.md to never read or print the contents of .env files.
B.
Delete the .env file before running Claude Code and restore it afterward.
C.
Extract secrets into environment variables, add sensitive config file patterns to the permissions.deny list in .claude/settings.json (e.g., Read(.env), Read(.env.*)), and run Claude Code in Plan Mode for sensitive sessions.
D.
Configure a PreToolUse hook that intercepts and blocks any file-read tool call targeting .env or secrets files by filename pattern.
A
Explanation
Incorrect. CLAUDE.md instructions are advisory and probabilistic the model generally follows them but cannot be guaranteed to do so in every context. Relying on a text instruction to protect sensitive credentials in an automated or CI/CD environment is insufficient as a security control.
B
Explanation
Incorrect. This is operationally fragile if the restore step fails or is forgotten, credentials are permanently lost. It breaks the development workflow and is not a maintainable security practice. It is a dangerous workaround, not an architectural solution.
C
Explanation
Correct. This implements a defence-in-depth approach using officially documented Claude Code mechanisms: (1) Environment variables keep secrets off the filesystem entirely; (2) The permissions.deny block in .claude/settings.json is the built-in, declarative mechanism for blocking file access patterns like Read(.env) and Read(.env.*) prevent Claude from reading matching files; (3) Plan Mode (--permission-mode plan) restricts the session to read-only, preventing any unintended file writes during sensitive review work.
D
Explanation
Partially correct. A PreToolUse hook provides strong, deterministic enforcement and is a valuable defence-in-depth layer. However, the permissions.deny block in .claude/settings.json is the simpler, officially recommended declarative approach that achieves the same goal without requiring custom shell scripting. For maximum security, combine both.
💡 Key Learning Point
Explanation: The correct approach is first, moving secrets out of raw code into environment variables is standard engineering hygiene. Second, .claude/settings.json permissions operate on a strict Deny → Ask → Allow hierarchy enforced by the local CLI engine. If a path matches a rule inside the deny array, Claude Code is physically blocked from reading or editing it, even if a user prompts it to do so. Combining this with Plan Mode gives the developer maximum oversight before any code changes are executed. In a 'Multi-Pass' code review architecture, a 'Style Agent' and a 'Logic Agent' both review a Pull Request. Why is this specialized multi-agent approach superior to a single general-purpose agent?
A.
It prevents the agents from reading each other's output, reducing confusion.
B.
It reduces the total token cost by splitting the workload.
C.
The multi-agent approach is faster because agents run in parallel.
D.
Each specialized agent can be given a focused system prompt and tool set, allowing it to apply deeper, more targeted expertise to its specific domain without the cognitive overhead of managing multiple review dimensions simultaneously.
A
Explanation
Incorrect. Agent isolation is not inherently beneficial in many architectures, agents benefit from reviewing each other's work (evaluator-optimizer pattern). The primary benefit of the multi-pass code review architecture is not isolation; it is specialisation each agent's focused domain expertise produces deeper analysis than a generalist.
B
Explanation
Incorrect. A multi-agent approach typically uses more total tokens than a single-agent approach each agent has its own system prompt, context setup, and output. The architectural benefit is quality improvement through specialisation, not cost reduction. Token costs are generally higher, not lower, for multi-agent systems.
C
Explanation
Incorrect (partially). Parallel execution is a secondary benefit that improves throughput, but it is not the primary reason the architecture is superior. Two poorly specified agents running in parallel produce poor results quickly. The primary advantage is the qualitative improvement in review depth enabled by specialisation, not the speed of parallel execution.
D
Explanation
Correct. Specialisation is the primary architectural advantage. Explanation
Incorrect. Increasing max_tokens only helps when the output is being truncated (indicated by stop_reason: 'max_tokens'). Explanation
Correct. A validation-retry loop is the standard, production-proven pattern for structured extraction.
